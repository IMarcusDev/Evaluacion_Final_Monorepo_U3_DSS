\section{Introducción}
El presente informe detalla el proceso de containerización, despliegue en un clúster de Kubernetes y auditoría de seguridad del sistema InvenTrack. Se documentan los pasos realizados para la creación de contenedores Docker para los componentes del sistema (backend, frontend y base de datos), la configuración de manifiestos de Kubernetes, el despliegue en un clúster local, y la configuración del Ingress para exponer la aplicación bajo el dominio \texttt{conjunta3p.espe.edu.ec}. Además, se presenta un análisis de seguridad siguiendo la metodología PTES (Penetration Testing Execution Standard), incluyendo la recopilación de inteligencia, modelado de amenazas, análisis de vulnerabilidades, explotación y post-explotación, así como las conclusiones y recomendaciones derivadas del proceso.

\subsection{Objetivo General}

El objetivo general de esta evaluación es realizar un despliegue seguro del sistema InvenTrack en un clúster de Kubernetes, asegurando la correcta containerización de sus componentes y evaluando su seguridad mediante pruebas de penetración siguiendo la metodología PTES. 

\subsection{Objetivos Específicos}
\begin{itemize}
  \item Realizar la containerización de los componentes del sistema InvenTrack (backend, frontend y base de datos) utilizando Docker.
  \item Configurar los manifiestos de Kubernetes necesarios para ejecutar InvenTrack en un clúster, incluyendo Deployments, Services, ConfigMaps, Secrets, PersistentVolumeClaims e Ingress.
  \item Configurar el Ingress para exponer la aplicación bajo el dominio \texttt{conjunta3p.espe.edu.ec} y asegurar la correcta resolución de DNS.
  \item Realizar una auditoría de seguridad del sistema InvenTrack siguiendo la metodología PTES, identificando vulnerabilidades y evaluando la efectividad de los controles de seguridad implementados.
\end{itemize}

\section{Dockerización de Componentes}

La containerización del sistema InvenTrack se organizó en tres componentes independientes: el backend (API REST en Node.js/Express), el frontend (aplicación React construida con Vite) y la base de datos MySQL. Para cada componente se definió una estrategia de empaquetado acorde con su función. El backend y el frontend se construyeron a partir de un \texttt{Dockerfile} propio, mientras que la base de datos se apoyó en la imagen oficial de MySQL 8.0, configurada por variables de entorno y volúmenes. En todos los casos se partió de imágenes base Alpine, que reducen el tamaño de la imagen resultante. A continuación se describen los Dockerfiles de cada componente y las decisiones de construcción aplicadas. Los términos técnicos de Docker y Kubernetes que aparecen en este informe se definen en el Glosario (Apéndice A), que puede consultarse para una mayor comprensión de los conceptos.

\subsection{Backend (Node.js/Express)}

\begin{lstlisting}[language=bash,caption={Dockerfile del Backend},label=lst:dockerbackend]
#Marcos Escobar
FROM node:20-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

RUN mkdir -p uploads \
  && addgroup -g 1001 -S app \
  && adduser  -u 1001 -S app -G app \
  && chown -R app:app /app
USER app

EXPOSE 4000

CMD ["node", "src/app.js"]
\end{lstlisting}

El Dockerfile del backend, presentado en el Listado \ref{lst:dockerbackend}, partió de la imagen \texttt{node:20-alpine}. Primero se copiaron los archivos \texttt{package*.json} y se ejecutó \texttt{npm ci --omit=dev}, de modo que la imagen incorpora solo las dependencias de producción (--omit=dev es la versión moderna de --production). Después se copió el código fuente y se creó el directorio \texttt{uploads}, destinado a las imágenes de producto que gestiona Multer. Un aspecto relevante para la seguridad fue la creación de un usuario sin privilegios (\texttt{app}, con UID y GID 1001) y la asignación de la propiedad del directorio de trabajo a dicho usuario. La instrucción \texttt{USER app} evitó que el proceso se ejecute como \texttt{root} dentro del contenedor, lo que reduce el impacto de una eventual intrusión. Por último se expuso el puerto 4000 y se definió el arranque del servidor con \texttt{node src/app.js}.

\subsection{Frontend (React/Vite)}

\begin{lstlisting}[language=bash,caption={Dockerfile del Frontend (multi-stage)},label=lst:dockerfrontend]
#Marcos Escobar
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
\end{lstlisting}

El Dockerfile del frontend, mostrado en el Listado \ref{lst:dockerfrontend}, aplicó una construcción en dos partes (multi-stage). En la primera parte, basada en \texttt{node:20-alpine}, se instalaron las dependencias con \texttt{npm ci} y se generó la versión estática de producción con \texttt{npm run build}, que Vite genera en el directorio \texttt{dist}. En la segunda etapa se utilizó la imagen \texttt{nginx:1.27-alpine} como servidor web. Solo los archivos compilados del directorio \texttt{dist} se copiaron a la ruta pública de Nginx, junto con una configuración personalizada (\texttt{nginx.conf}) que define el enrutamiento de la aplicación de página única y agrega cabeceras de seguridad. De este modo, la imagen final no contiene el código fuente ni las herramientas de compilación, lo que disminuye su tamaño y su superficie de exposición. El contenedor del frontend expone el puerto 80.

\subsection{Base de Datos (MySQL)}

La base de datos se ejecutó a partir de la imagen oficial \texttt{mysql:8.0}, sin un Dockerfile propio, dado que la configuración requerida se resolvió por variables de entorno y volúmenes. La persistencia de la información se garantizó con un volumen montado en \texttt{/var/lib/mysql}, de modo que los datos sobreviven al reinicio o a la recreación del contenedor. El esquema inicial se cargó de forma automática: los archivos de inicialización se montaron en el directorio \texttt{/docker-entrypoint-initdb.d}, que la imagen de MySQL ejecuta en la primera puesta en marcha cuando el directorio de datos está vacío. Ese conjunto incluyó el archivo \texttt{init.sql}, con la definición de las tablas, y un archivo de datos de ejemplo (\texttt{seed\_01\_electronica.sql}) que inserta usuarios, categorías, proveedores, productos y movimientos de kardex. Con este mecanismo, el sistema dispuso de datos iniciales sin una carga manual posterior. La orquestación de los tres contenedores se realizó con Docker Compose, que además definió un \textit{healthcheck} sobre MySQL para que el backend inicie solo cuando la base de datos está operativa.

Los puertos publicados confirman la exposición del frontend en el 5173, del backend en el 4000 y de MySQL en el 3306.

\section{Manifiestos de Kubernetes}

El despliegue de InvenTrack en Kubernetes se definió mediante un conjunto de manifiestos en formato YAML. Los archivos se numeraron del \texttt{00} al \texttt{06} para fijar el orden de aplicación, de modo que los recursos base (namespace, secretos y configuraciones) existieran antes que los componentes que dependen de ellos. Cada archivo agrupó los recursos de una misma categoría: el namespace, los Secrets, los ConfigMaps, la base de datos MySQL con su volumen, el backend, el frontend y el Ingress. Esta separación permitió aplicar los manifiestos de forma ordenada con \texttt{kubectl apply}. A continuación se describe cada tipo de recurso y las decisiones de configuración aplicadas. El significado de cada objeto y parámetro de Kubernetes citado puede consultarse en el Glosario (Apéndice A).

\subsection{Namespaces}

Todos los recursos de InvenTrack se agruparon en un namespace propio llamado \texttt{conjunta-desarrollo-seguro}, cuya definición se presenta en el Listado \ref{lst:namespace}. El namespace proporcionó un aislamiento dentro del clúster, de manera que los objetos del sistema quedaron separados de otras cargas de trabajo. Cada manifiesto posterior declaró de forma explícita este namespace en su campo \texttt{metadata}, lo que evitó que los recursos se crearan en el espacio \texttt{default}. Con ello se logró que la eliminación del namespace bastara para retirar por completo el despliegue.

\begin{lstlisting}[caption={Definición del Namespace (00-namespace.yaml)},label=lst:namespace]
apiVersion: v1
kind: Namespace
metadata:
  name: conjunta-desarrollo-seguro
\end{lstlisting}

\subsection{Deployments y Services}

El sistema se estructuró en tres Deployments, uno por componente, cada uno acompañado de un Service de tipo \texttt{ClusterIP} que expuso el recurso solo dentro del clúster. La Tabla \ref{tab:deployments} resume las características principales de cada Deployment. El frontend se configuró con dos réplicas para tolerar la caída de un pod, mientras que el backend y la base de datos operaron con una sola réplica, dado que MySQL escribe sobre un volumen que no admite acceso concurrente desde varios pods.

\begin{table}[H]
  \centering
  \caption{Resumen de los Deployments de InvenTrack}
  \label{tab:deployments}
  \begin{tabularx}{\textwidth}{l l c c X}
    \toprule
    \textbf{Deployment} & \textbf{Imagen} & \textbf{Réplicas} & \textbf{Puerto} & \textbf{Service} \\
    \midrule
    mysql    & \texttt{mysql:8.0}             & 1 & 3306 & ClusterIP \\
    backend  & \texttt{inventrack-backend:1.0}  & 1 & 4000 & ClusterIP \\
    frontend & \texttt{inventrack-frontend:1.0} & 2 & 80   & ClusterIP \\
    \bottomrule
  \end{tabularx}
\end{table}

El Deployment del backend, mostrado en el Listado \ref{lst:backend}, incorporó varias medidas de seguridad y de disponibilidad. Un \texttt{securityContext} obligó a que el contenedor se ejecutara como usuario sin privilegios (UID y GID 1001) y con \texttt{runAsNonRoot}, en concordancia con el usuario creado en el Dockerfile. Además, se deshabilitó el montaje automático del token de la cuenta de servicio (\texttt{automountServiceAccountToken: false}) para reducir la superficie de ataque en caso de intrusión. Un \textit{initContainer} llamado \texttt{wait-for-mysql} retrasó el arranque del backend hasta que la base de datos respondiera, y las sondas \texttt{readinessProbe} y \texttt{livenessProbe} sobre la ruta \texttt{/api/health} permitieron a Kubernetes verificar el estado del proceso. Las variables de entorno se inyectaron desde el ConfigMap y el Secret, sin valores en texto plano dentro del manifiesto.

\begin{lstlisting}[caption={Deployment y Service del backend (04-backend.yaml)},label=lst:backend]
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: conjunta-desarrollo-seguro
spec:
  replicas: 1
  selector:
    matchLabels: { app: backend }
  template:
    metadata:
      labels: { app: backend }
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 1001
        runAsGroup: 1001
        fsGroup: 1001
      initContainers:
        - name: wait-for-mysql
          image: mysql:8.0
          command:
            - sh
            - -c
            - |
              until mysqladmin ping -h mysql --silent; do
                echo "esperando a mysql..."; sleep 2;
              done
      containers:
        - name: backend
          image: inventrack-backend:1.0
          ports:
            - containerPort: 4000
          env:
            - name: DB_HOST
              valueFrom: { configMapKeyRef: { name: inventrack-config, key: DB_HOST } }
            - name: DB_PASSWORD
              valueFrom: { secretKeyRef: { name: inventrack-secrets, key: DB_PASSWORD } }
            - name: JWT_SECRET
              valueFrom: { secretKeyRef: { name: inventrack-secrets, key: JWT_SECRET } }
          readinessProbe:
            httpGet: { path: /api/health, port: 4000 }
          livenessProbe:
            httpGet: { path: /api/health, port: 4000 }
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { cpu: 500m, memory: 256Mi }
---
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: conjunta-desarrollo-seguro
spec:
  type: ClusterIP
  selector: { app: backend }
  ports:
    - port: 4000
      targetPort: 4000
\end{lstlisting}

Los Deployments de la base de datos y del frontend siguieron un patrón similar. En ambos casos se deshabilitó el token de la cuenta de servicio y se definieron límites de CPU y memoria, con el fin de evitar el consumo excesivo de recursos. El frontend, al servir contenido estático mediante Nginx, requirió menos recursos y solo una sonda de disponibilidad sobre la ruta raíz. Cada Service asoció su selector de etiquetas con los pods correspondientes, lo que permitió que los componentes se comunicaran por nombre de servicio (\texttt{mysql}, \texttt{backend} y \texttt{frontend}) dentro del clúster.

\subsection{ConfigMaps y Secrets}

La configuración del sistema se separó en dos tipos de recursos según su confidencialidad. Los parámetros no confidenciales se almacenaron en el ConfigMap \texttt{inventrack-config}, presentado en el Listado \ref{lst:configmap}, que definió el puerto del backend, el nombre del host de la base de datos, el usuario y el nombre de la base. Adicionalmente, un segundo ConfigMap (\texttt{mysql-initdb}) contuvo el archivo \texttt{init.sql} con el esquema y los datos iniciales, y se montó en el directorio de inicialización de la imagen de MySQL. De este modo, la información de configuración quedó desacoplada del código y de las imágenes.

\begin{lstlisting}[caption={ConfigMap de configuración (02-configmap.yaml)},label=lst:configmap]
apiVersion: v1
kind: ConfigMap
metadata:
  name: inventrack-config
  namespace: conjunta-desarrollo-seguro
data:
  PORT: "4000"
  DB_HOST: "mysql"
  DB_USER: "root"
  DB_NAME: "inventrack"
\end{lstlisting}

Los datos confidenciales se aislaron en el Secret \texttt{inventrack-secrets}, mostrado en el Listado \ref{lst:secret}, que agrupó la contraseña de la base de datos, la clave de firma de los tokens JWT y la clave de la API de Groq. El Secret se definió como \texttt{Opaque} y se empleó el campo \texttt{stringData} (véase el Apéndice A para la definición de ambos términos), que Kubernetes codifica en base64 al persistirlo. Conviene señalar que esta codificación no constituye un cifrado, por lo que los valores mostrados son de ejemplo y, en un entorno de producción, deberían gestionarse con un sistema de secretos dedicado. Tanto el ConfigMap como el Secret se consumieron mediante referencias \texttt{configMapKeyRef} y \texttt{secretKeyRef} en las variables de entorno de los contenedores, de manera que ningún valor confidencial apareció en los manifiestos de los Deployments.

\begin{lstlisting}[caption={Secret con credenciales (01-secrets.yaml)},label=lst:secret]
apiVersion: v1
kind: Secret
metadata:
  name: inventrack-secrets
  namespace: conjunta-desarrollo-seguro
type: Opaque
stringData:
  DB_PASSWORD: "password"
  JWT_SECRET: "jwt_secret"
  GROQ_API_KEY: "groq_api_key"
\end{lstlisting}

\subsection{PersistentVolumeClaim (PVC)}

La persistencia de datos se resolvió con dos PersistentVolumeClaim, de modo que la información sobreviviera al reinicio o a la recreación de los pods. El primero, \texttt{mysql-pvc}, solicitó 2 Gi de almacenamiento y se montó en \texttt{/var/lib/mysql} para conservar la base de datos. El segundo, \texttt{uploads-pvc}, solicitó 1 Gi y se montó en \texttt{/app/uploads} del backend para almacenar las imágenes de producto que gestiona Multer. Ambos volúmenes utilizaron el modo de acceso \texttt{ReadWriteOnce}, tal como se muestra en el Listado \ref{lst:pvc}. Por esta razón, el Deployment de MySQL adoptó la estrategia de actualización \texttt{Recreate}, que detiene el pod anterior antes de crear el nuevo y evita que dos pods intenten escribir sobre el mismo volumen de forma simultánea.

\begin{lstlisting}[caption={PersistentVolumeClaim de la base de datos (03-mysql.yaml)},label=lst:pvc]
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
  namespace: conjunta-desarrollo-seguro
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 2Gi
\end{lstlisting}

\subsection{Ingress}

El acceso externo a InvenTrack se canalizó mediante un único recurso Ingress, denominado \texttt{inventrack-ingress}, cuya definición se presenta en el Listado \ref{lst:ingress}. Este recurso empleó la clase \texttt{nginx} y publicó la aplicación bajo el dominio \texttt{conjunta3p.espe.edu.ec}. El enrutamiento se definió por rutas: las peticiones a \texttt{/api} y a \texttt{/uploads} se dirigieron al Service del backend en el puerto 4000, mientras que el resto de las rutas se enviaron al Service del frontend en el puerto 80. De esta forma, un solo punto de entrada atendió tanto la interfaz de usuario como la API. La anotación \texttt{proxy-body-size} se fijó en \texttt{10m} para permitir la carga de imágenes de producto sin exceder el límite por defecto del controlador Ingress.

\begin{lstlisting}[caption={Definición del Ingress (06-ingress.yaml)},label=lst:ingress]
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: inventrack-ingress
  namespace: conjunta-desarrollo-seguro
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
spec:
  ingressClassName: nginx
  rules:
    - host: conjunta3p.espe.edu.ec
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: backend, port: { number: 4000 } }
          - path: /uploads
            pathType: Prefix
            backend:
              service: { name: backend, port: { number: 4000 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: frontend, port: { number: 80 } }
\end{lstlisting}

\section{Despliegue en el Clúster y Configuración de Ingress}

El despliegue de InvenTrack se realizó sobre un clúster local de Kubernetes gestionado con Minikube. Esta sección describe las características del clúster, el controlador Ingress empleado, la resolución del dominio \texttt{conjunta3p.espe.edu.ec} y las evidencias del despliegue. Asimismo, se documenta una incidencia surgida durante la primera puesta en marcha y la forma en que se resolvió, dado que constituye parte del procedimiento seguido.

\subsection{Descripción del Clúster}

El clúster se levantó con Minikube 1.38.1 sobre un equipo con Arch Linux, empleando el controlador de Docker (\textit{driver} \texttt{docker}) y el mismo Docker como entorno de ejecución de contenedores. Se configuró un único nodo con rol de plano de control, que ejecutó la versión 1.35.1 de Kubernetes y quedó accesible en la dirección \texttt{192.168.49.2}. Esta topología de un solo nodo resultó suficiente para el alcance del entregable, ya que reprodujo el comportamiento de un clúster real sin la complejidad de una instalación multinodo.

Dado que Minikube utiliza un demonio de Docker propio, aislado del demonio del sistema anfitrión, las imágenes construidas en el equipo no estuvieron disponibles de forma automática dentro del clúster. Por esta razón, tras construir las imágenes del backend y del frontend se cargaron de manera explícita en Minikube con el comando \texttt{minikube image load}. El Listado \ref{lst:buildload} presenta la secuencia aplicada. Este paso fue determinante, puesto que su omisión provocó la incidencia descrita en la subsección \emph{Incidencia durante el Despliegue: ImagePullBackOff}.

\begin{lstlisting}[language=bash,caption={Construcción y carga de las imágenes en Minikube},label=lst:buildload]
# Construir las imágenes con el Docker del host
docker build -t inventrack-backend:1.0 ./backend
docker build -t inventrack-frontend:1.0 ./frontend

# Cargar las imágenes dentro del demonio de Minikube
minikube image load inventrack-backend:1.0
minikube image load inventrack-frontend:1.0

# Verificar que quedaron disponibles en el clúster
minikube image ls | grep inventrack
\end{lstlisting}

\subsection{Controlador Ingress}

El enrutamiento externo se apoyó en el controlador Ingress Nginx, habilitado como complemento (\textit{addon}) de Minikube. Al activar el complemento, Minikube desplegó el controlador \texttt{ingress-nginx-controller} en el namespace \texttt{ingress-nginx}, que quedó en estado \texttt{Running} y atendió las peticiones dirigidas a la dirección del clúster. El recurso Ingress de InvenTrack declaró la clase \texttt{nginx}, de modo que este controlador fue el encargado de aplicar las reglas de enrutamiento por ruta definidas en el Listado \ref{lst:ingress}. El Listado \ref{lst:addoningress} muestra los comandos empleados para habilitar y verificar el controlador.

\begin{lstlisting}[language=bash,caption={Habilitación y verificación del controlador Ingress Nginx},label=lst:addoningress]

\subsection{Incidencia durante el Despliegue: ImagePullBackOff}
\label{sec:incidencia}

Tras aplicar los manifiestos, los pods del backend y del frontend no alcanzaron el estado \texttt{Running}, sino que quedaron en \texttt{ImagePullBackOff}, mientras que la base de datos operó con normalidad. La Figura \ref{fig:pullbackoff} muestra este estado, en el que los Deployments \texttt{backend} y \texttt{frontend} reportaron cero réplicas disponibles. La causa se identificó en los registros del backend, presentados en la Figura \ref{fig:logspull}, donde el mensaje indicó que el contenedor fallaba al intentar descargar la imagen (\textit{trying and failing to pull image}).

El origen del problema fue que las imágenes \texttt{inventrack-backend:1.0} e \texttt{inventrack-frontend:1.0} existían en el demonio de Docker del equipo anfitrión, pero no dentro del demonio de Minikube. Como los Deployments declararon la política \texttt{imagePullPolicy: IfNotPresent} y las imágenes no estaban presentes en el clúster, el \textit{kubelet} intentó descargarlas de un registro público (Docker Hub), donde no existen, y la descarga fue rechazada. En consecuencia, el Ingress no dispuso de destinos sanos para el backend ni para el frontend, por lo que respondió con el código \texttt{503 Service Temporarily Unavailable}, tal como se observa en la Figura \ref{fig:curl503}.

\begin{figure}[H]
  \centering
  \includegraphics[width=1\linewidth]{Verificacion_1.png}
  \caption{Pods del backend y el frontend en estado \texttt{ImagePullBackOff}.}
  \label{fig:pullbackoff}
\end{figure}

\begin{figure}[H]
  \centering
  \includegraphics[width=1\linewidth]{Verificacion_3.png}
  \caption{Registros del backend con el fallo de descarga de la imagen.}
  \label{fig:logspull}
\end{figure}

\begin{figure}[H]
  \centering
  \includegraphics[width=1\linewidth]{Verificacion_2.png}
  \caption{Respuesta \texttt{503} del Ingress y estado de los PersistentVolumeClaim.}
  \label{fig:curl503}
\end{figure}

La solución consistió en cargar las imágenes en el demonio de Minikube con \texttt{minikube image load}, según la secuencia del Listado \ref{lst:buildload}, y reiniciar los Deployments afectados para que el \textit{kubelet} volviera a crear los pods con las imágenes ya presentes en el clúster. El Listado \ref{lst:fix} detalla los comandos aplicados. Una vez presentes las imágenes, la política \texttt{IfNotPresent} evitó cualquier intento de descarga externa y los pods alcanzaron el estado \texttt{Running}.

\begin{lstlisting}[language=bash,caption={Resolución de la incidencia ImagePullBackOff},label=lst:fix]
# Cargar las imágenes ausentes en el clúster
minikube image load inventrack-backend:1.0
minikube image load inventrack-frontend:1.0

# Reiniciar los Deployments para recrear los pods
kubectl rollout restart deployment/backend deployment/frontend \
  -n conjunta-desarrollo-seguro
\end{lstlisting}
